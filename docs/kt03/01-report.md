# КТ-03 Данные и транзакции PostgreSQL

## Запуск

Нужны Docker Compose, Go 1.22+ и make. Все команды выполняются из корня проекта.

```sh
make kt03-all
make kt03-package
```

Полный запуск создаёт данные двух режимов, проверяет запросы и транзакции, выполняет измерения. Повторный запуск пересоздаёт только базы стенда с префиксом `transport_kt03`. База предыдущего спринта `transport` отдельная. CSV остаются в `data/`; в архив включены генератор и контрольные суммы.

Перед упаковкой проверяются обязательные файлы, версия и согласованность наборов, контрольные суммы SQL, наличие всех измеренных планов и правильность медиан. Начало повторного этапа удаляет его прежнюю отметку PASS; после ошибки она не используется при сборке. Makefile в архиве содержит команды КТ-03 из `kt03.mk`.

| Команда | Назначение |
|---|---|
| `make kt03-dev` | 75 000 сообщений в `transport_kt03_dev`, проверки, запросы и планы |
| `make kt03-load` | 3 млн сообщений в `transport_kt03`, проверки, запросы и планы |
| `make kt03-scenarios` | COMMIT, ROLLBACK, конкурентность и диагностика блокировки |
| `make kt03-compare` | INSERT и COPY на ранее созданном наборе разработки |
| `make kt03-report` | Обновление этого отчёта из сохранённых результатов |
| `make kt03-package` | Архив `submission/KT-03.zip` |

Отдельный запуск генератора с другим seed:

```sh
go run ./cmd/kt03 generate --mode dev --seed 42 --data data/example
go run ./cmd/kt03 load --database transport_kt03_example --data data/example
```

Команда `load` пересоздаёт указанную базу; допустим только префикс `transport_kt03`. Параметр `--rows` предназначен для небольших экспериментов; штатные режимы запускаются без него. `--runs` задаёт число измерений, по умолчанию семь.

Окружение измерений: PostgreSQL 17.10, ARM64, Docker Desktop, 15 CPU и 10418151424 байт памяти Docker; отдельных лимитов контейнера нет. `shared_buffers` — 128 МиБ, `work_mem` — 4 МиБ, JIT включён. Образ закреплён digest в compose.yaml. Версии инструментов и настройки сохранены в [environment.json](../../artifacts/kt03/environment.json). Абсолютное время зависит от ресурсов и состояния кэша.

## Генератор и распределение

Go-генератор использует отдельный псевдослучайный поток с seed 20261011. Опорное время — 2026-10-11T13:30:00+07:00, часовой пояс UTC+7. Даты, UUID и отпечатки содержимого определяются входными параметрами. Текущее время компьютера не участвует в генерации. Для каждого CSV сохраняются количество строк и SHA-256; загрузчик проверяет суммы до пересоздания базы. Автотест сравнивает повторную генерацию с тем же seed и проверяет изменение данных при другом seed.

| Данные | Разработка | Нагрузка |
|---|---:|---:|
| Дней | 7 | 30 |
| Автобусов и устройств | 20 | 100 |
| Плановых рейсов | 560 | 12000 |
| Плановых точек | 11200 | 240000 |
| Прохождений | 6672 | 154420 |
| Сообщений `message_key` | 75000 | 3000000 |

Крупнейшая таблица — `message_key`. Это синтетическая выборка реестра обработки, без сырых документов MongoDB. Рейсы содержат 20 точек с интервалом две минуты; на наряд приходится четыре рейса. Два из 12 маршрутов выбираются с вероятностью 70%, остальные — 30%. Сначала создаются принятые сообщения для каждого прохождения, затем остальные сообщения до требуемого объёма. Для остальных сообщений устройство в 70% случаев выбирается среди первых 10% парка, в остальных случаях — среди всего парка. Ожидаемая доля популярных устройств в этой части потока — 73%; сообщения прохождений распределены по фактически назначенным автобусам.

У сообщений различаются дни и время суток. У сообщений прохождений время формирования совпадает с фактом прохождения, приём — через секунду. У остальных сообщений в исторические дни 70% времени приёма выбирается из утренних и вечерних часов, остальные значения — из всех суток. Последний день ограничен временем до опорного снимка. Целевые доли результатов всего набора: 92% `accepted`, 5% `invalid`, 3% `stale`; вероятности оставшейся части учитывают уже созданные сообщения прохождений. При `invalid` неизвестные время формирования и установка равны NULL; при `stale` сообщение задержано на 20 минут. В нагрузочном наборе фактически получено:

| Результат | Строк |
|---|---:|
| accepted | 2760549 |
| invalid | 149188 |
| stale | 90263 |

Исторические выполнения включают завершение по телеметрии, ручное завершение, невыполнение и неизвестный результат. В последнем дне присутствуют `waiting`, `running`, `review`, запланированные и отменённые наряды. Опоздания встречаются чаще опережений; есть открытые и закрытые отклонения, а также недостоверные прохождения. Ручное завершение не создаёт искусственных прохождений. Неизвестный результат не считается невыполнением.

CSV содержат согласованный снимок истории. Порядок загрузки учитывает внешние ключи; ограничения и триггеры остаются включены. После загрузки сверяются количества всех таблиц, выполняется `check_model()` и проверяются распределения. Снимок плана фиксируется вместе с выполнением. Итоги: [разработка](../../artifacts/kt03/dev/verification-dev.json), [нагрузка](../../artifacts/kt03/load/verification-load.json). Загрузка нагрузочного набора через COPY вместе с фиксацией заняла 63.90 с; проверка SHA-256, создание схемы и ANALYZE измерены за пределами этого интервала.

Дополнительная проверка требует у каждого прохождения принятое сообщение с тем же устройством, UUID и временем формирования. Фактические события не могут быть позже опорного времени, а признак непроверенных результатов закрытого наряда должен соответствовать наличию выполнения `review`.

Генератор версии 2 учитывает БП-10: первая точка фиксируется в окне от −2 до +15 минут относительно плана. Опережение −3 минуты допускается на следующих точках. После неразрешённого `review` следующие рейсы наряда не начинаются по телеметрии: они остаются ожидающими до истечения срока, затем также требуют проверки. [SQL-проверки](../../sql/kt03/check_business_rules.sql) считают нарушения независимо от генератора; в обоих наборах счётчики равны нулю. [Регрессионные примеры](../../artifacts/kt03/business-regression.json) подтверждают, что эти проверки обнаруживают слишком ранний старт и запуск после неразрешённого `review`.

## Проверки при пакетной загрузке

В миграции 004 отложенный строчный триггер запускал проверку всей модели для каждой изменённой строки. На пробной вставке 2 000 сообщений вставка заняла 30.795 мс, COMMIT — 1732.678 мс.

Миграция 005 заменяет эти вызовы на очередь `transport_private.model_check_queue`: триггер после оператора ставит одну проверку на транзакцию; отложенный триггер очереди выполняет прежнюю `check_model()` под прежней advisory-блокировкой и удаляет запись очереди. На таком же пробном наборе COMMIT занял 7.653 мс. Это один диагностический запуск каждого размера, а не статистическая оценка ускорения.

`SET CONSTRAINTS ALL IMMEDIATE` выполняет ожидающую проверку. Следующие изменения снова проверяются; откат к точке сохранения откатывает и изменения очереди. Роли приложения не имеют доступа к очереди. Сохранены проверки FK, CHECK, UNIQUE, EXCLUDE и неизменности истории. Порядок работы отложенных триггеров соответствует [CREATE TRIGGER](https://www.postgresql.org/docs/17/sql-createtrigger.html) и [SET CONSTRAINTS](https://www.postgresql.org/docs/17/sql-set-constraints.html).

Проверки: [исходная регрессия](../../artifacts/kt03/regression.json), [режимы ограничений и откаты](../../tests/kt03/batch_validation.sql), [пробные измерения](../../artifacts/kt03/pilot.json). Полная проверка модели по-прежнему сериализуется общей блокировкой; эта доработка устраняет повторение проверки внутри пакета, но не превращает механизм в высокопроизводительный обработчик телеметрии.

## Пять бизнес-запросов

Общие параметры нагрузочных примеров: `period_start=2026-09-12T00:00:00+07:00`, `period_end=2026-10-12T00:00:00+07:00`. Интервал полуоткрытый: начало включено, конец исключён. Для рейсов период определяется плановым началом, для сообщений — первым приёмом, для списка отклонений — обнаружением. Полные результаты и параметры находятся в [queries](../../artifacts/kt03/load/queries/).

### Соблюдение расписания по маршрутам

Бизнес-вопрос: сколько рейсов выполнено и какая доля достоверных прохождений попала в график по каждому маршруту? Параметры: начало и конец периода. [SQL](../../sql/kt03/queries/01_schedule.sql).

K — достоверные прохождения завершённых рейсов в диапазоне от −2 до +5 минут к плану; N — все их достоверные прохождения. Доля равна 100 × K/N, при N=0 — NULL. Статусы считаются отдельно, ручное завершение без прохождений не повышает показатель. Пример одной строки:

```json
  "planned_points": 86640,
  "planned_trips": 4332,
  "review_trips": 930,
  "route_id": 1,
  "unreleased_trips": 40,
  "unreliable_points": 283
}
```

## Транзакция и конкурентность

Сценарии используют отдельную базу и небольшой фиксированный пример КТ-02. Запуск: `make kt03-scenarios`.

Успешная подмена между рейсами закрывает назначения старого наряда, создаёт новые назначения, закрывает старый наряд и выпускает резервный. Выполнения и первоначальный снимок плана сохраняются, UUID операции регистрируется в той же транзакции. После COMMIT проверяются статусы, назначения, выполнения и запись операции. [SQL](../../sql/kt03/scenarios/commit.sql), [состояния до и после](../../artifacts/kt03/scenarios/commit.json).

Во втором сценарии у резервного автобуса просрочен допуск. Операция успевает выполнить промежуточные изменения, затем выпуск отклоняется с SQLSTATE 23514. Клиент выполняет явный ROLLBACK. Снимки всех строк нарядов, назначений, выполнений, планов и реестра операций до и после равны. Значения последовательностей не сравниваются: выдача identity-номера не откатывается. [SQL](../../sql/kt03/scenarios/rollback.sql), [журнал ошибки](../../artifacts/kt03/scenarios/rollback.txt), [сравнение](../../artifacts/kt03/scenarios/rollback.json).

Конкурентный сценарий запускает два отдельных соединения. Первый выпуск удерживает блокировку до команды COMMIT от координатора. Вторая сессия пытается выпустить тот же автобус в другом наряде и ждёт. Координатор дожидается подтверждённого ожидания через `pg_stat_activity` и `pg_blocking_pids`, сохраняет диагностику, затем разрешает первой сессии COMMIT. Вторая получает SQLSTATE 23505 по индексу `one_vehicle_on_line`. Итог — ровно один наряд на линии у автобуса. [Результат](../../artifacts/kt03/scenarios/concurrency.json).

## Планы и измерения

Сравнение выполнено на одном нагрузочном наборе после ANALYZE. Для каждого варианта два прогревочных выполнения и 7 измеряемых. В таблице — медиана серверного `Execution Time` из `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, включая расходы инструментирования. Это измерения с прогретым кэшем. Доставка результата клиенту не входит во время. Данные между вариантами не меняются, результаты сравниваются целиком; оптимизатор не принуждается к заданному типу сканирования.

| Запрос | До, мс | После, мс | Отношение до/после |
|---|---:|---:|---:|
| schedule | 881.932 | 337.322 | 2.61 |
| history_hot | 0.777 | 0.166 | 4.68 |
| history_rare | 5.875 | 0.174 | 33.76 |

`history_hot` и `history_rare` — два значения параметра одного запроса, для устройств device-001 и device-100. Исходные измерения: [JSON](../../artifacts/kt03/load/bench/measurements.json), [CSV](../../artifacts/kt03/load/bench/comparison.csv), [планы всех запусков](../../artifacts/kt03/load/plans/).

В отчёте по маршрутам [исходный вариант](../../sql/kt03/queries/01_schedule_before.sql) использует `trip_summary`: в плане шесть коррелированных подзапросов выполняются по 12 000 раз. В новом запросе выбранные рейсы материализуются один раз, а счётчики точек вычисляются общей группировкой. Число обращений к уже загруженным страницам в первых сохранённых планах уменьшилось с 1796501 до 487465. Новый план записывает 965 временных блоков при `work_mem=4MB`; несмотря на это, устраняет значительную повторную работу. [До](../../artifacts/kt03/load/plans/schedule-before-01.json), [после](../../artifacts/kt03/load/plans/schedule-after-01.json).

Для истории устройства добавлен индекс `(device_id, first_received_at DESC, message_id DESC)`. До изменения PostgreSQL читает индекс времени `message_key_retention`, отбрасывает сообщения других устройств и использует Incremental Sort. После — читает подходящие сообщения в требуемом порядке по `message_device_received`, без отдельной сортировки. Неравномерность данных особенно заметна на редком устройстве. [Индекс](../../sql/kt03/optimize.sql), [до](../../artifacts/kt03/load/plans/history_rare-before-01.json), [после](../../artifacts/kt03/load/plans/history_rare-after-01.json).

## Дополнительные эксперименты

### Ожидание блокировки

Диагностический запрос сохраняет PID, состояние, ожидаемое событие, блокирующие PID и строки `pg_locks` двух сессий. Вторая сессия ожидает событие `transactionid` типа `Lock`; `pg_blocking_pids` указывает на первую сессию. Это ожидание блокировки строки `planning_guard`, через которую проходят операции выпуска. После COMMIT ожидание заканчивается, а уникальный индекс отклоняет второй выпуск. [Диагностический SQL](../../sql/kt03/scenarios/locks.sql), [снимок ожидания](../../artifacts/kt03/scenarios/lock-wait.json), [журналы сессий](../../artifacts/kt03/scenarios/).

### Пакетный INSERT и COPY

Сравнивается один CSV с 75000 сообщениями на схеме 005 без нового индекса оптимизации. Перед каждым запуском очищается только `message_key` в отдельной базе эксперимента. Остальные таблицы, ограничения и индексы одинаковы. Оба метода выполняются в одной транзакции; INSERT объединяет по 1 000 строк в оператор, COPY читает CSV через стандартный ввод. Методы чередуются между повторами. После каждой загрузки сравнивается количество и отпечаток всех строк.

| Стратегия | Медиана, мс |
|---|---:|
| COPY | 1068.018 |
| INSERT по 1 000 строк | 1306.772 |

Один прогрев и 7 измерений каждого метода. Здесь измеряется полное клиентское время загрузки: чтение CSV, преобразование в SQL для INSERT, передача, вставка и COMMIT. Создание схемы, очистка и проверка отпечатка находятся вне измеряемого интервала. Для основного наполнения выбран COPY. Сырые результаты: [load-comparison.json](../../artifacts/kt03/load-comparison.json). Назначение COPY для массовой загрузки описано в [документации PostgreSQL](https://www.postgresql.org/docs/17/populate.html).
