# КТ-04 · Эксплуатация PostgreSQL

Учебный стенд проекта «Мониторинг городского транспорта» использует PostgreSQL 17 и отдельный Compose-проект `transport-kt04`. Шаблон преподавателя отсутствует в репозитории, поэтому для стенда использована собственная конфигурация. Сервисы `primary`, `replica`, `restore` и `pitr` доступны с хоста на `127.0.0.1:55404–55407` соответственно. Для клиента выделен отдельный контейнер, чтобы он мог зафиксировать ошибку подключения даже при остановленном сервере. [Конфигурация стенда](../../deploy/kt04/compose.yaml)

## Запуск

Нужны macOS или Linux, Go 1.22+ и запущенный Docker Engine с Compose. Из корня репозитория:

```sh
go build -o bin/kt04 ./cmd/kt04
TARGET_ARCH=arm64 # для Docker на Intel/AMD заменить на amd64
CGO_ENABLED=0 GOOS=linux GOARCH="$TARGET_ARCH" go build -o bin/kt04-client ./cmd/kt04-client
CGO_ENABLED=0 GOOS=linux GOARCH="$TARGET_ARCH" go build -o bin/kt04-migrate ./cmd/kt02
```

До первой инициализации задайте постоянный абсолютный путь `KT04_SECRETS_DIR` вне репозитория. Например, `export KT04_SECRETS_DIR="$HOME/.local/share/transport-kt04/secrets"`. Без переменной используется временный каталог `/private/tmp/transport-kt04-secrets`. Команда `setup` создаёт пароли, файлы `pgpass` и сертификаты или проверяет существующие. Для уже инициализированного стенда используйте прежний каталог. Дампы также храните вне репозитория, указав `KT04_BACKUP_DIR` или оставив значение по умолчанию `/private/tmp/transport-kt04-backups`.

Для нового стенда на другом компьютере можно использовать `export KT04_BACKUP_DIR="$HOME/.local/share/transport-kt04/backups"`, чтобы не зависеть от наличия `/private/tmp`. Архитектуру Docker показывает `docker info --format '{{.Architecture}}'`: `aarch64` соответствует `arm64`, `x86_64` — `amd64`.

```sh
./bin/kt04 setup
./bin/kt04 init
./bin/kt04 security
./bin/kt04 backup
./bin/kt04 replication
./bin/kt04 analytics
./bin/kt04 lag
./bin/kt04 failures
./bin/kt04 pitr
./bin/kt04 package
```

Этот порядок рассчитан на первое прохождение. `init` применяет миграции, загружает учебные данные и создаёт роли. `backup` и `pitr` используют отдельные экземпляры для восстановления. Сценарий PITR запускается последним и использует отдельный том и WAL-архив primary.

## Что проверяет стенд

| Этап | Проверка |
| --- | --- |
| `security` | Пять отдельных входов, разрешённые и запрещённые операции, отказ Go-клиента от superuser, RLS для двух водителей, TLS с проверкой CA и имени сервера, отказ от подключения без TLS. [Отчёт](../../artifacts/kt04/security.json) |
| `backup` | Логический дамп, восстановление в чистый экземпляр, сравнение данных и прав, проверки ограничений и последовательностей. [Отчёт](../../artifacts/kt04/restore.json) |
| `replication` | Выпуск наряда приложением, поступление изменения на физическую реплику, чтение аналитиком, отказ записи на standby. Повтор с тем же UUID проверяет идемпотентность и единственность записи аудита. [Отчёт](../../artifacts/kt04/replication.json) |
| `lag` | Измерение отставания применения WAL при массовой загрузке и времени догоняния. [Отчёт](../../artifacts/kt04/lag.json) |
| `analytics` | Один и тот же отчёт выполняется аналитиком на primary и replica после догоняния WAL; результаты совпадают. [Отчёт](../../artifacts/kt04/analytics-proxy.json) |
| `failures` | Отдельные остановки replica и primary, наблюдение за клиентом, запуск узлов и проверка целостности. [Отчёт](../../artifacts/kt04/failures.json) |
| `pitr` | Восстановление из физической базовой копии и WAL к заданной точке с проверкой строк до и после неё. [Отчёт](../../artifacts/kt04/pitr.json) |

`kt04_admin` читает данные, аудит и статистику, включая `pg_monitor`. Для полного логического восстановления с владельцами и ACL используется отдельная служебная учётная запись `postgres`. `kt04_app` читает отчёт, статус наряда и журнал запросов и может выпустить наряд через бизнес-функцию. `kt04_analyst` читает транспортную схему и отчёты, в том числе на реплике. Каждая роль водителя видит только собственные наряды. Аудит сохраняет имя LOGIN, идентификатор наряда, время и переход статуса. [Настройка прав, RLS и аудита](../../sql/kt04/security.sql) · [Проверки Go](../../internal/kt04/security.go) · [Дополнительные SQL-проверки](../../tests/kt04/security.sql)

Сводки выполненных этапов появляются в [artifacts/kt04](../../artifacts/kt04/). Для диагностики и восстановления используйте [runbook](runbook.md).

## Результат прогона 4 ноября 2026

Проверено на Mac mini ARM64, PostgreSQL 17.11. Все восемь этапов с отчётами прошли. Для КТ-04 используются Go, SQL и Docker; Python не требуется. Go-клиент вызывает настоящий `psql`, веб-интерфейс в проверках не участвует.

- Роли, RLS и TLS: разрешения и запреты подтверждены отдельными TCP-подключениями.
- Restore: данные, владельцы, права базы и объектов совпали; ограничения и последовательности работают.
- Репликация: новая запись выпуска дошла на standby; повтор UUID оставил одну запись аудита.
- Lag: 100 000 синтетических строк в отдельной учебной таблице, максимум наблюдённого отставания 30 004 808 байт WAL. Загрузка заняла 322 мс, проверка догоняния — 215 мс. Последнее включает время диагностических запросов, это не точная сетевая задержка.
- Отказы: клиент записал ошибку и возобновил чтение. От команды запуска до успешной проверки: replica около 0,77 с, primary около 0,21 с. Это остановка контейнеров с сохранёнными томами, без автоматического переключения.
- PITR: цель `2026-11-04 19:44:11.270209 +07:00`. В восстановленной базе есть `before-target`, нет `after-target`; исходная база сохранила оба маркера.

Готовый комплект: `submission/KT-04.zip`. Секреты и дамп в него не входят. Конфигурация репликации собственная: предоставленный инфраструктурный шаблон отсутствует.
